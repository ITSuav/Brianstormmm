# Final Frontend Plan

## Delivery Boundary

The frontend owns the command-center experience, asset loading, UI contracts, and documentation. The algorithm team owns drone route optimization and MATSim simulation outputs.

## Non-Negotiable Data Rule

All central visual and geospatial layers must come from real data products:

- GEE DEM, Sentinel-2, slope, water/vegetation/risk layers are generated by `scripts/export_gee_assets.py`.
- Blender renders and browser 3D terrain are generated from the same GEE heightmap and Sentinel-2 texture sources.
- Route and MATSim panels remain interface slots until the algorithm team supplies results.
- City/building extrusion stays blocked until real footprint-height data is supplied.

## Execution Plan

1. Generate real GEE assets for the Hong Kong study area.
2. Render the Blender fallback visual and GLB from the GEE assets.
3. Build the browser digital twin as an interactive Three.js local-scene terrain.
4. Keep route upload and MATSim integration as typed boundaries.
5. Build and lint before pushing to GitHub.

## UI Direction

The design follows a restrained aerospace command-center language: black operational canvas, high-density panels, Google-color operational accents, and an interactive 3D central terrain view. Technical provenance stays in documentation and manifests rather than the operator-facing big screen.

## Handoff Needs

- Algorithm route JSON examples from the route planning group.
- MATSim scenario/run output schema.
- Official Hong Kong building heights or 3D city data.
- Official no-fly/restricted zones and obstacle layers.
- Real 3DGS captures if SuperSplat scenes are expected in the demo.
